## 1. 目标与范围

### 1.1 取号保证

同一个本地 Git 仓库及其全部登记 worktree 共用编号分配。四类编号分别递增：

|类别|规范位置|创建入口|
|---|---|---|
|Task：`tNNN`|`docs/tasks/tNNN_{slug}/`|`task.py add`|
|Pending：`pNNN`|`docs/pending/pNNN_{slug}.md`|`pending.py new`|
|Finding：`dNNN`|`docs/findings/dNNN_{slug}.md`|`findings.py new`|
|Spike：`sNNN`|`docs/spikes/sNNN_{slug}/`|`spikes.py new`|

1. worktree A 创建 `d037_alpha` 后，worktree B 创建另一条 finding 必须使用 `d038` 或更大编号，即使 A 的条目尚未暂存或提交。
2. 已有 `d036` 随分支出现在多个 worktree，属于正常副本，不应误报重复。`p037` 与 `d037` 属于不同序列，也不冲突。
3. 取号只读取本机已有数据，不执行 `fetch`、`pull`、GitHub API 或其他网络请求，不要求配置远端。
4. 本机保存的远端分支记录也参与避重。例如，上次拉取留下的 `origin/main` 已有 `d050`，即使本地 `main` 只有 `d041`，下一次仍分配 `d051`。
5. GitHub 上尚未拉取到本机的编号不属于本次保证范围；不处理独立 clone 之间的并发取号。

### 1.2 历史与回收边界

1. 保留本地可达 Git 历史扫描，用于计算最大占用编号。旧 commit 中存在重复，只取最大值，不报错、不改写历史。
2. 本地分支、已保存的远端分支、tag、主仓及登记 worktree HEAD 可达历史中的规范条目路径，均提供占用编号。已提交条目随后被删除，只要编号仍能从这些历史路径读出，就不再分配。
3. 未提交、未启动的 task 草稿被 `purge` 删除后，如果编号不在上述历史、任何 worktree 文件或 index 中，可以自然回收。
4. 不建立独立编号账本或持久高水位文件；不承诺保留已经完全不可达的提交、缺失的浅克隆历史，或仅存在于旧历史总账正文中的编号。
5. 当前仍存在的旧总账由同步迁移解析，其条目编号参与本轮迁移取号；日常取号不加载旧总账正文解析器。

### 1.3 同步修复范围

1. 同步在当前主干工作区自动修复 `d`、`p`、`s` 重复编号，同时更新文件名、元数据和能确定目标的普通文档引用。
2. 当前重复 `tNNN` 仍按原计划阻断：task 编号关联分支、执行记录与受保护核心资产，本次不自动改 task 编号。`tNNN` 新建取号仍统一改造。
3. 保留同步前工作区和 index 干净、额外 worktree 先收尾的要求，不批量改写其他分支或其他 worktree。
4. 其他当前协议本地分支内部仍有重复时，按原计划阻断并列出分支与路径；旧 commit、已保存远端分支中的重复不作为同步阻断条件。
5. `AC-NNN`、review 报告内局部 finding 序号、spec slug、ADR 日期与 slug、attempt 和会话 UUID 不纳入本次全仓序列。

## 2. 当前缺口与修复方向

本节为静态源码核对结果，未在原消费仓重现实验。

1. `repo_task/lifecycle.py::cmd_add` 已持公共 ID 锁，但只从主仓当前 task 目录计算最大号，未与其他入口采用相同扫描规则。
2. `_id_scan.py` 当前以本地分支 tip 和登记 worktree 文件为主，并以当前 schema 筛选来源；已保存远端分支、被后续提交删除的条目路径、仅留在 index 中的条目未完整参与占用计算。
3. 当前重复编号会阻断普通新建；同步缺少自动修复这些重复的完整路径。现有提交 hook 检查待提交快照，完整手动修正并暂存后可以通过，不属于无法解除的死锁。
4. 重复检查散落在旧总账拆分、实体迁移计划构建和最终验收中。只在 `entity-storage` 后增加消重阶段，前置步骤仍可能先报错，导致消重无法执行。
5. 同步事务只备份声明路径。改号引起的普通文档引用修改也必须提前纳入备份；不能让用户在 `apply` 后补改，再期待原指纹和单 commit 验收通过。

## 3. 本地统一取号设计

### 3.1 统一扫描定义

在 `_id_scan.py` 集中定义四类条目及其历史目录：

- 当前目录：`docs/tasks`、`docs/pending`、`docs/findings`、`docs/spikes`。
- 历史目录：沿用上述目录，并涵盖 `docs/archive/tasks`、`docs/archive/pending`、`docs/pending/todo`、`docs/pending/parked`、`docs/archive/spikes`。
- 只识别规范编号与符合实体位置的条目路径。目录型编号取实体目录，不把目录内附件文件名或任意嵌套示例目录计为实体。

占用扫描读取：

1. 本地 `refs/heads/*`、本机已有 `refs/remotes/*`、tag 及登记 worktree HEAD 可达的本地历史路径。
2. 当前本地分支和本机已有远端分支 tip；排除远端 `HEAD` 等符号引用的重复枚举。
3. 主仓及所有登记 worktree 的磁盘条目，包括未跟踪条目。
4. 每个 worktree 各自的 index，包括已暂存后又从磁盘删除的条目。

不因来源缺少当前 schema 就忽略其规范路径占用号。旧协议正文解析仍只存在于同步迁移。

扫描应按来源批量收集路径并计算四类最大值，避免同一次分配反复遍历完整历史。首次实现不新增缓存、后台进程或缓存失效协议。

### 3.2 占用计算与当前校验分离

|操作|重复处理|
|---|---|
|`scan_occupied_max_id`：计算最大占用号|相同编号出现多次仍正常取最大值，供分配和迁移共用|
|`scan_max_id`：普通创建入口|先检查当前协议来源的目录与当前编号，再取最大占用号|
|迁移计划构建|保留全部来源条目，给重复组生成新编号，不因待修复重复提前退出|
|最终验收、提交和合入检查|检查最终当前快照，重复即失败|

当前校验按每个分支、磁盘快照、index 快照分别执行，不把多个快照简单拼接后计数：

- 同一路径在不同分支、worktree、磁盘和 index 中出现，正常参与最大值计算，不算多份冲突文件。
- 单个当前快照内，两个不同条目占用同类同号，属于重复。
- 磁盘与 index 分别校验，避免把尚未暂存的合法改名与 index 中旧路径误判为同一快照重复；占用计算仍合并两者编号。
- 历史提交与已保存远端分支仅提供占用号，不要求清理其重复数据。

### 3.3 分配流程与并发

四个创建入口共用 `TASK_ID_LOCK_NAME`，在 Git common directory 的同一排他锁内完成：

```text
取得公共 ID 锁
→ 检查当前数据
→ 扫描本机已有占用编号
→ 计算目标类别最大号 + 1
→ 生成并验证条目
→ 发布到最终路径
→ 释放锁
```

新条目发布后才释放锁，下一次分配必然可见。不得先返回编号、释放锁，再创建文件。

`task.py add` 保留主仓写权、slug 检查和 task 模板校验；仅替换其独立最大号计算，继续遵守 `purge` 的自然回收规则。

### 3.4 Git 路径读取

- 路径输出使用支持 `-z` 的 Git 命令及 NUL 分隔解析，不按换行或空白切分文件名。
- `worktree list` 使用支持路径完整读取的格式；不能通过 `.strip()` 破坏合法路径。
- 非路径型命令不机械追加 `-z`，按各命令实际接口处理。
- 历史路径只做编号提取，不逐个历史 commit 执行当前 schema 或重复校验。
- 保留受控 Git 环境，避免 hook/IDE 的 `GIT_*` 环境把扫描重定向到其他仓库。

## 4. 同步消重与旧格式转换共用实体迁移

### 4.1 迁移入口收口

扩展现有 `entity-storage`，统一负责当前实体清单、旧总账拆分、旧目录转换与重复编号修复。

1. 移除独立注册的 `pending-ledger`、`findings-ledger` 阶段，将当前仍存在的旧总账输入并入 `entity-storage` 计划。
2. 复用 `legacy_ledgers.py` 的正文解析与完整性检查。解析得到的条目以来源文件和条目位置区分，不在解析阶段因同号丢弃、合并或拒绝条目。
3. 不新增排在后面的 `duplicate-ids` 阶段，也不增加 `check_duplicates=False` 等最终验收绕过开关。
4. 迁移辅助代码可放入 `template_sync/duplicate_ids_migration.py`，仅负责改号表计算和明确的内容转换，由现有实体迁移调用，不拥有独立事务或运行期兼容路径。
5. `workflow-schema` 仍在实体迁移之前；预检继续使用其预计生成的 task 内容，避免未执行前要求旧 task 已符合新格式。

相关迁移顺序变为：

```text
legacy-state → workflow-schema → entity-storage → state-root
→ goal-snapshot → conventions → agents-zones → specs-layout
→ reviews → adr → retired-hooks → retired-docs
```

### 4.2 先确定最终结果，再写盘

`entity-storage` 的只读计划按以下顺序构建：

`status`、`plan` 和 `apply` 共用此计划构建结果。迁移检测不再先对原始输入执行严格目标验收并把可修复重复标成阻断；严格目标验收用于计划生成的最终结果和实际落盘结果。

1. 读取当前实体、当前旧目录和当前旧总账，保留每份来源内容。迁移内需要转换的旧元数据沿用已有解析规则。
2. 校验来源可读、路径和元数据合法；元数据声明与来源文件名不一致时仍报错，不将身份损坏伪装成普通重复。
3. 按类别和原编号分组；`d`、`p`、`s` 同号多条进入消重计划，`t` 重复列为阻断项。
4. 计算各类本地最大占用号，并并入本轮旧总账解析出的全部编号。避免尚未写出的总账条目与新号冲突。
5. 为每条来源确定最终编号、最终路径和最终内容，再构建引用修改与删除清单。
6. 验证最终目标路径、编号、元数据和内容完整性，保证不会覆盖未被计划接管的已有文件。

旧目录搬迁直接采用改号后的最终路径，不先搬迁到冲突位置，再尝试补救。相同来源路径与同名目标的情况也不能靠覆盖或丢弃内容解决。

### 4.3 保留者与新号规则

1. 按 `d`、`p`、`s` 顺序处理；各类别内按原编号升序处理重复组。
2. 沿用原计划的稳定保留规则：当前分支可达历史中，来源首次新增记录的提交时间较早者保留原号；没有提交记录者排后；时间相同按来源相对路径及旧总账条目位置排序。
3. 普通文件查询新增记录时处理改名历史；spike 以 `report.md` 为查询对象。旧总账中多个条目共享文件历史时，以条目位置稳定区分。
4. 其余条目从该类最大占用号加一顺序分配。一次计划内维护各类别递增值，不为每个重复条目重扫完整历史。
5. 计划仅计算，不预留编号。`apply` 在锁内重新核对输入并确定本轮实际映射，输出实际结果供提交前审阅；不直接使用已经过期的预览编号。

示例，假设本地可见最大 finding 为 `d041`：

```text
d037_alpha.md → 保留 d037_alpha.md
d037_beta.md  → d042_beta.md
d038_gamma.md → 保留 d038_gamma.md
d038_delta.md → d043_delta.md
```

### 4.4 条目内容修改

|类别|迁移动作|
|---|---|
|Finding|修改文件名和围栏外 H1 中对应编号，正文其他内容保留|
|Pending|修改文件名、front matter 的 `pid` 和 H1 中对应编号；保留 slug、状态、依据和闭环信息|
|Spike|修改目录名和 `report.md` 的 `sid`；H1 含原编号时同步替换；代码与附件保留|

- H1 不含编号时保持原样，例如现有 spike 标题 `# Spike report`。存在其他不一致身份声明时按非法输入处理，不能盲目替换数字。
- 不对全文执行裸编号字符串替换，不修改代码块里的无关数字。
- 迁移以完整计划写入和搬迁，目标存在时必须确认属于本轮计划；禁止覆盖未知内容。
- 源内容成功写入目标后才能移除源文件；所有操作处于同一事务中。
- 不为旧编号或旧路径保留软链、别名文件或运行期回退查找。
- Markdown 统一交由 `apply` 格式化，迁移内部不单独调用格式化器。

### 4.5 阻断与正常待办

以下情况为迁移前阻断项：

- 同步工作区或 index 不干净、存在未结束事务或额外登记 worktree。
- 当前 task 编号重复，或其他当前协议本地分支内部仍有重复。
- 实体目录、条目或需要改写的文档为软链；spike 内存在影响搬迁安全的软链。
- 条目非规范命名、内容不可读、必须元数据损坏、来源编号与声明不一致。
- 旧总账解析不完整、最终目标冲突、无法证明来源内容全部保留。

当前主干 `d`、`p`、`s` 重复属于正常迁移待办，不属于上述阻断项。历史和已保存远端分支的重复只参与最大号计算。

预检应始终执行分支与输入合法性检查，不能因为当前工作区没有迁移待办，就跳过其他分支阻断项。

## 5. 引用更新、事务和最终验收

### 5.1 引用更新范围

1. 从改号表得到精确的旧路径与新路径。检查当前消费项目已跟踪 Markdown，包括实体目录、README、handoff、spec 等普通项目文档。
2. 自动更新能确定指向被改号条目的完整仓库相对路径，以及可解析的文档相对路径；保留链接的锚点等后缀，并校验路径边界，避免误替换相似文件名。
3. 裸 `d037`、`p037`、`s037` 不能全仓替换，因为保留原号的条目仍使用该编号。无足够路径上下文的引用保留，列出文件、行号和改号映射供复核，不声称这些引用已经全部修复。
4. `docs/tasks/*/` 中受保护的 `task.md`、`progress.md`、`handoff.json`、`review_*.md` 沿用既有只读保护，仅报告相关历史引用；本次不改其编号、内容和所有权规则。
5. 模板硬同步文件由固定模板源提供，不将消费项目编号替换扩展到模板内容；不扫描 Git 内部、依赖目录、缓存、忽略文件或二进制附件。
6. 迁移报告分别列出实体改号、已更新普通文档、裸编号待复核引用和受保护历史引用。报告不构成旧编号运行期别名。

### 5.2 事务覆盖与锁

1. 保留 `FileTransaction`。实体迁移声明路径加入 `docs/findings`、两个当前旧总账及原有实体迁移目录。
2. 只读计划给出本轮实际要改写的额外引用文件。`apply` 在 `transaction.begin` 前将这些文件并入备份与验收路径，不用整个仓库作为笼统备份根。
3. 本轮 `apply` 使用确定后的实体与引用计划，执行前核对来源内容；不能在开始写盘后发现新的范围外文件并直接修改。
4. 同步先持既有控制面锁，再持公共 ID 锁。ID 锁覆盖占用扫描、计划确定、备份、实体及引用写入、最终验证和失败回滚，结束本轮 `apply` 后释放，避免备份恢复删除同期创建条目。
5. 所有入口采用一致锁顺序：控制面锁在前，ID 锁在后。同步验证中需要创建条目的测试使用隔离仓库，避免子进程等待父进程持有的当前仓库 ID 锁。
6. 失败由同一事务恢复源文件、最终路径、普通文档及原有 common 状态，不为消重再开一份事务或独立恢复入口。

### 5.3 保留现有指纹保护

指纹是事务所管文件及状态的校验值，用于比较 `apply` 完成后到 `accept` 之间是否又发生变化。

```text
确定全部改号和引用修改
→ 备份
→ 执行迁移与模板同步
→ 格式化
→ 严格验收并运行契约测试
→ 记录最终指纹
→ 用户审阅结果
→ 经批准单次提交
→ transaction accept
```

改号与确定的引用修正均在记录指纹前完成，因此无需改动指纹算法或放松 `accept`。不把提交前手动补改引用作为正常成功路径。

提交后若需要撤销，沿用既有同步取消或 Git revert 流程；不在 HEAD 改变后强行用文件备份覆盖现场。

### 5.4 严格验收与幂等

1. `validate_current_entities` 保持严格语义，不接收跳过重复检查参数；补全 finding 的路径、软链、命名和编号检查。
2. `validate_snapshot_ids` 覆盖 `t`、`p`、`d`、`s`，供 pre-commit、commit-msg、待合入验证与集成门禁共用。
3. 最终检查编号、文件名和元数据一致；最终目标无覆盖丢失；本轮自动更新的引用指向存在的最终路径。
4. 再次规划同一结果，不再出现需要改号的条目，也不再次修改编号。
5. 无重复只表示没有消重写入；若还有模板或其他迁移变更，正常产生同步 diff。只有整轮同步无交付差异且满足既有状态条件时才收尾为 `no_op`。

## 7. 测试与验收

### 7.1 本地取号

|场景|预期|
|---|---|
|两个进程跨 worktree 同时创建 finding、pending 或 spike|同类编号不重复|
|两个进程同时从主仓创建 task，其他 worktree 或分支已有更大 task 编号|主仓写权不变，两个新号不同且均避开已有编号|
|A 中最高编号尚未暂存或提交，B 创建|B 避开 A 的编号|
|仅在某 worktree index 中有条目，磁盘已删除|编号仍被占用|
|多个 worktree 继承同一路径，磁盘和 index 同时出现|不误报多份冲突条目|
|磁盘条目改名但 index 尚未更新|分别校验快照，占用取并集|
|其他本地分支、本机已有远端分支或 tag 独有较大号|下一编号大于该占用号|
|detached worktree 独有提交或未提交条目|正常避重|
|规范条目来自没有当前 schema 的来源|参与占用计算，不加载旧正文解析器|
|已提交的规范路径条目随后删除，历史仍可达|不再分配其编号|
|旧 commit 或已保存远端分支中曾有重复|最大值计算正常，当前合法时允许创建|
|未入库、未启动草稿被 purge，所有占用来源均不存在|允许自然回收|
|未配置远端，或远端地址当前不可访问|取号正常且不发网络请求|

使用本地测试仓建立已有远端分支记录，再拒绝任何联网命令，验证取号只读本机信息。四类编号独立测试，保留规范 padding、目录深度、失败不发布等既有契约。完整历史按单轮批量扫描，测试防止对每个重复条目反复全量扫描。

### 7.2 同步消重

1. Issue #96 场景：当前 `d037` 两条、`d038` 两条，其他最大号为 `d041`；预览显示两个改号，apply 生成 `d042`、`d043`，正文与普通文档精确路径更新。
2. 安装并实际运行 pre-commit、commit-msg；一次提交迁移和模板结果，`accept` 成功；随后新建获得 `d044`。
3. pending 同步更新文件名、`pid` 和对应 H1；spike 更新目录和 `sid`，不含编号的标题保持原样，代码与附件字节不变。
4. 当前重复与旧目录搬迁同时发生；旧总账重复、旧总账与实体文件同号、旧目录同名目标冲突均由统一计划分配最终新号，来源内容全部保留。
5. 改号涉及实体目录外的 README、handoff 或 spec 引用时，全部确定修改均在事务范围内，并通过单 commit 和指纹验收。
6. 裸编号不盲改，受保护核心资产不改；报告明确列出这些引用，不以报告代替已承诺的精确路径修复。
7. 无当前重复但其他当前协议分支有重复时，仍在零写盘预检阶段阻断；额外 worktree、重复 task、软链、非规范名称及损坏元数据按规则阻断。
8. 重复仅存在旧 commit 或已保存远端分支时，不阻断当前同步；最大号仍参与新号选择。
9. 无重复、无其他变化时保持整轮 `no_op`；无重复但模板有变化时正常同步；再次 apply 不重复改号。

### 7.3 事务、锁与回归

- 在来源转换、实体发布、源删除、目录搬迁、引用修改、格式化和最终验收处注入失败，验证整个事务恢复，不留新增路径或丢失附件。
- 同步期间并发创建应等待公共 ID 锁；成功或失败回滚结束后再创建，验证不会撞号或被恢复过程删除。
- 验证现有指纹能接受本轮内部完成的引用修改，也能拒绝 apply 后额外修改，无需放松验收。
- 更新 `factory_tests/sync/test_single_commit_sync.py` 的阶段参数与失败夹具，使其真实覆盖统一后的 entity-storage，不保留已删除阶段名称。
- 总账相关旧测试改为经统一实体迁移调用，保留正文完整性等有效断言；与自动消重目标冲突的“同号必定拒绝迁移”断言改成验证实际修复结果。
- 保留 Python 3.9 注解可导入等项目仍要求的工具链契约；不为旧阶段名称、旧解析写盘接口或原重复阻断行为维护兼容层。

后续修改产物后，必须在工厂根执行全量门禁。前置条件为已安装 pytest、pytest-xdist 及测试所需工具；成功条件是契约测试与工厂集成测试全部通过，失败则停止交付并修复：

## 8. 实施顺序与成功标准

1. **统一本地扫描和四类创建入口** → 验证：跨 worktree 并发、暂存区、已保存远端记录、本地历史与 purge 契约，取号期间零网络请求。
2. **收口实体迁移计划和总账输入** → 验证：先决定改号后最终路径，当前重复与旧格式转换同时完成，不覆盖或丢弃来源内容。
3. **将精确引用修改纳入原事务** → 验证：目录外引用可回滚，实际 hooks、单 commit、指纹和 accept 完整通过。
4. **更新相关文档并完成全量回归** → 验证：无独立旧阶段兼容壳，无跳过重复检查的最终验收分支，无未执行测试被标为通过。

最终成功标准：同一 Git common directory 下，工具新建条目在本机可见占用范围内不撞号；同步一次修复当前主干可自动处理的重复并正常提交接受；历史重复不阻断，取号全程不联网。
