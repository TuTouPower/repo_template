# repo_template 宏观设计审阅报告

## 摘要

本次审阅从仓库分层、agent/skill 目录结构、任务工作流、模板初始化与升级、状态恢复、验证门禁和多宿主适配等角度展开，不评价具体代码实现质量。

总体判断：仓库已经具备一套较完整的规格驱动开发框架。工厂与消费仓边界、skill 单一正文源、worktree 隔离、派生索引、独立 review、最终内容指纹、Git 原生 merge 和危险操作授权等设计具有明确价值，应当保留。

当前主要矛盾不是流程数量不足，而是已有流程之间出现了组合断点：

- 初始化复制可能携带 secret、本机运行态和旧同步状态。
- skill 的“禁止模型调用”与父流程调用子 skill 相互冲突。
- backlog 合并可能删除下游硬依赖。
- running attempt 缺少同 task 执行互斥。
- 模板同步的自举和 prep 位于备份、回滚事务之外。
- 模板 contract 与消费项目业务验证之间仍存在“形式绿”通道。
- 多份权威文档已经出现实际语义漂移。
- 本机运行态、同步态缺少清晰的重建和迁移路径。

因此，下一阶段的优先方向应当是**修复端到端闭环、减少权威重复、明确适用边界**，而不是继续增加状态、hook、skill 或调度能力。

## 1. 审阅范围与判断口径

### 1.1 审阅范围

本次重点检查以下内容：

- 工厂根与 `repo/` 消费仓产物的边界。
- `AGENTS.md`、`.repo_template/docs/usage.md`、`.repo_template/docs/architecture.md` 的权威划分。
- `.repo_template/skills/`、`.agents/skills/`、`.claude/skills/`、`.opencode/commands/` 的组织方式。
- task 从创建、排程、执行、review、finish、cleanup 到 integrate 的完整生命周期。
- pending、finding、spike、spec 和 archive 的配套闭环。
- attempt、ledger、goal、worktree 和 handoff 的状态关系。
- 模板复制、初始化、同步、自举、迁移、验证、回滚和版本追踪。
- 工厂全量测试与消费仓 contract 测试的分工。
- Claude、Kimi Code、OpenCode 等宿主的调用语义差异。

### 1.2 问题性质

报告将问题分为三类：

|类型|含义|
|---|---|
|契约可直接确认|从现行文档、CLI 契约、测试契约或官方宿主文档即可确认，不依赖猜测实现细节|
|兼容性风险|由宿主版本或运行能力差异触发，尚需对应宿主端到端验证|
|设计边界与采用成本|属于有意取舍，但当前适用场景、默认路径或恢复说明不足|

### 1.3 审阅限制

本轮采用只读静态审阅、CLI 帮助契约核对和官方文档核对，没有执行完整业务流程、全量 pytest 或三宿主端到端测试。因此：

- 报告可以指出契约矛盾、缺失路径和可构造的失败场景。
- 报告不宣称当前测试失败。
- 涉及宿主实际行为的条目，应在修复前后增加真实端到端验证。

## 2. 总体架构评价

### 2.1 当前系统已经超出“轻量仓库骨架”

当前消费侧包含：

- 15 个 canonical skill。
- 15 个 `.agents` 入口、15 个 `.claude` 软链入口和 15 个 OpenCode 生成命令。
- 23 个 `task.py` 一级子命令，另有 attempt 等嵌套命令。
- 10 步新项目初始化流程。
- task 业务状态、attempt 执行状态、Git 分支与 worktree、handoff、review、ledger、goal 等多层契约。
- 创建 commit、执行 commit、merge commit 等不同阶段的提交边界；单独排程时还会增加调度 commit。

这些机制并非没有价值，但仓库实际定位更接近：

> 面向高可追溯、高门禁、规格驱动、本机多会话开发的 task 编排系统。

如果目标是为所有项目提供一个轻量起点，当前默认形态偏重；如果目标本来就是上述场景，则大部分复杂度属于有意成本，应通过渐进披露和闭环修复降低使用难度，而不是简单删除机制。

### 2.2 当前最值得保留的设计

- 工厂私有笔记与消费仓产物分离，`docs_repo/` 不进入产物。
- canonical skill 只有一份正文，`.claude` 与 `.agents` 使用软链，OpenCode 使用薄生成层。
- task 状态以 task front matter 为权威，index 为派生缓存，降低跨分支索引冲突。
- 每个 task 使用独立 worktree，有效状态读取考虑 worktree、未合并分支和主干。
- review 绑定最终交付内容，AC evidence 必须覆盖当前 spec。
- merge 使用 Git 原生事务，执行授权与 merge/push 授权分离。
- 消费侧问题上报与工厂侧根因定位分离，职责和信任边界清楚。
- 工厂保留决策日志，能够避免重复讨论已经否决或已经落地的方案。

## 4. 高优先级问题

### H-01：初始化复制的是工作区，不是干净产物

**结论**

当前初始化命令从工厂工作区 `repo/` 直接复制文件。该目录不仅可能包含 Git 跟踪的模板文件，也可能包含工厂验证消费体验时产生的 secret、运行态、同步状态和宿主状态。

**证据**

- 工厂规则允许直接在 `repo/` 验证消费体验：`AGENTS.md:6`。
- 初始化命令只排除 `.git/`、`.scratch/`、`.pytest_cache/` 和 `__pycache__/`：`repo/README.md:11-21`。

- `.env`、`.env.*`、`docs/runtime/`、`.commandcode/`、`.repo_template/sync_state.json` 都属于可预期的本机文件：`repo/.gitignore:9-25`。
- 工厂根还显式忽略 `repo/docs/runtime/`、`repo/.claude/state/` 和 `repo/.repo_template/sync_state.json`：根 `.gitignore:12-15`。
- 初始化后文假设复制结果“不带 `sync_state.json`”，但复制命令没有提供这个保证：`repo/README.md:41`。

**影响**

- `.env` 等 secret 可能被带入新项目。`.gitignore` 只能防止提交，不能阻止复制行为。
- 新消费仓可能继承错误的 `template_source`，后续同步指向意外来源。
- dispatch ledger、goal 快照和宿主状态可能污染新项目的初始状态。
- 当前 Git 跟踪产物较干净，并不能消除从 dirty 工作区复制产生的风险。

**改进建议**

1. 默认只导出 Git 跟踪的 `repo/`，让 Git 跟踪清单成为分发唯一事实源，例如使用 `git archive`。
2. dirty 工作区复制仅作为显式开发模式，不作为普通用户初始化路径。
3. 若必须保留 rsync，集中维护分发清单或完整 exclude 列表，并在复制后断言：
    - 不存在 `.env` 和真实 `.env.*`。
    - 不存在 `docs/runtime/`。
    - 不存在 `.repo_template/sync_state.json`。
    - 不存在 `.claude/state/` 和 `.commandcode/`。
4. 初始化末尾增加软链校验、doctor 和 contract 烟测。

**验收建议**

构造一个同时含有 tracked 模板文件、`.env`、runtime、sync state、宿主状态和缓存的工厂产物目录。执行标准初始化后，目标仓只能包含预期分发物，软链必须有效，且不得出现 secret 或旧状态。

### H-02：显式触发门禁与父子 skill 组合冲突

**结论**

全部消费侧 skill 都禁止模型调用，但多个核心流程又要求模型继续调用子 skill。当前设计把“禁止未经用户授权的自动触发”和“禁止父流程通过原生 Skill 工具组合”绑定在了同一个开关上。

**证据**

- 所有 15 个消费侧 skill 都包含 `disable-model-invocation: true`。
- 契约测试只检查该字段存在：`repo/.repo_template/tests/test_contract_suite.py:107-119`。
- `task-run` 要求调用 `task-work` 和 `task-integrate`：`repo/.repo_template/skills/task-run/SKILL.md:9-36`。
- `repo-template-sync` 要求重新读取并执行 core：`repo/.repo_template/skills/repo-template-sync/SKILL.md:29-31`。
- `bug-to-pending`、`task-from-pending` 也会继续调用 `task-create` 或其他子流程。

官方语义：

- [Kimi Agent Skills 文档](https://www.kimi.com/code/docs/en/kimi-code-cli/customization/skills.html)接受 `disable-model-invocation` 作为字段别名。
- [Kimi Skill 工具文档](https://www.kimi.com/code/docs/en/kimi-code-cli/reference/tools.html)明确说明，带禁用标记的 skill 会被模型 `Skill` 工具拒绝。
- [Claude Skills 文档](https://code.claude.com/docs/en/skills)同样说明该字段阻止 Claude 通过 Skill 工具调用。
- OpenCode 对“隐藏自动推荐”和“按精确名称加载”的处理语义不同，不能直接假定三宿主行为一致。

**影响**

- 用户显式启动父 skill 后，父流程仍可能无法通过原生工具加载子 skill。
- 不同宿主或模型可能分别采取中断、要求用户再次调用、直接读取文件等策略，导致核心流程行为不一致。
- 当前测试只验证配置文本，没有验证最重要的父子调用链。

**改进建议**

1. 区分“公开用户入口”和“内部组合流程”。
2. 内部组合不要依赖宿主原生 Skill 调用：
    - 最小方案是明确规定父流程读取哪个 canonical 子流程文档，以及如何传递参数和授权。
    - 更清晰的长期方案是把内部 runbook 移出 skill registry，由公开 wrapper 读取。
3. 不要简单删除所有 `disable-model-invocation`，否则会重新开放未授权自动触发面。
4. 建立真实角色注册表，分别表达：
    - 可由用户直接调用。
    - 可作为父流程子节点。
    - 直接调用所需前置条件。
5. 为每个受支持宿主增加行为测试，而不是只检查 frontmatter。

**验收建议**

在 Claude、Kimi Code、OpenCode 分别验证：

- 自然语言不会未经批准触发高风险入口。
- 用户显式调用 `task-run` 后，完整父子链能够执行。
- `repo-template-sync` 能进入刷新后的 core。
- 子流程收到的 tid、attempt、execution_id 和授权范围不发生变化。
- 内部流程不会以不符合设计的方式出现在公开入口中。

### H-03：task-merge 会删除下游硬依赖

**结论**

当前 backlog 合并流程通过删除来源引用解决悬挂关系，却没有先把下游依赖改指合并目标。这会改变任务图的语义，而不仅是清理无效引用。

**证据**

`repo/.repo_template/skills/task-merge/SKILL.md:17-19` 要求：

1. 扫描全部 backlog。
2. 清除对来源 tid 的 `depends_on` 和 `conflicts_with` 引用。
3. drop 非目标来源。
4. 仅口头提示重新运行 `task-schedule`。

依赖又是 `start` 的硬门禁：`repo/.repo_template/docs/architecture.md:13-17,33-41`。

**可构造场景**

```text
t003.depends_on = t001
t001 + t002 合并为 t004
```

合并后：

- t003 对 t001 的依赖被删除。
- t001 被 drop。
- 如果没有立即重新排程，t003 可以先于 t004 启动。

图校验能够发现缺失引用和环，但无法发现一条已经被删除的语义依赖。

**改进建议**

1. 合并时把下游 `depends_on` 中的非目标来源改指目标 tid。
2. 对改指后的依赖去重，并检查自依赖和环。
3. 冲突关系可以重新评估，但不能与硬依赖采用同样的删除策略。
4. 将合并后的排程和图校验设为完成的必要条件，而不是口头建议。
5. 不需要恢复已经删除的 `schedule_status` 字段。

**验收建议**

至少覆盖：

- 单下游依赖改指。
- 多下游依赖改指。
- 合并后依赖去重。
- 自依赖拒绝。
- 依赖环拒绝。
- 目标 tid 保留和新建目标 tid 两种情况。

### H-04：running attempt 缺少执行互斥

**结论**

当前设计能够阻止重复 start 或重复 reserve，但没有阻止第二个会话在原 attempt 仍运行时接续同一个 task-work。

**证据**

- 多会话手动并发是明确支持的使用方式：`repo/.repo_template/docs/usage.md:75`。
- `task-run` 遇到已有现场时会执行恢复：`repo/.repo_template/skills/task-run/SKILL.md:24`。
- running attempt 的恢复动作是“以原 identity 继续 task-work”：`repo/.repo_template/scripts/repo_task/recovery.py:56-60`。
- “current attempt 尚未 terminal 时不得 reserve 新 attempt”只阻止新 attempt，不阻止两个执行者复用原 attempt：`repo/.repo_template/skills/task-run/SKILL.md:32`。

**影响**

两个会话可能同时写入同一个 worktree，并竞争：

- 实现和测试文件。
- review 报告。
- task.md 和 handoff。
- 执行 commit。
- terminal/report 事件。

这属于多会话宣传场景下的执行正确性问题。

**改进建议**

1. 最低成本方案：恢复 running attempt 前，必须明确确认原会话已经停止，并展示原 identity、worktree 和现场摘要。
2. 更可靠方案：增加 per-task 执行锁或租约，覆盖完整 task-work，而不仅是 reserve 瞬间。
3. 锁或租约只解决互斥，不需要重新引入自动调度器。
4. 对“会话仍在运行”和“会话已经崩溃”分别给出恢复路径。

**验收建议**

使用两个真实会话或两个执行上下文同时恢复同一 tid，验证只有一个能够进入 task-work；另一个必须得到明确的所有权冲突或存活确认提示。

### H-05：同步自举和 prep 位于统一恢复事务之外

**结论**

同步器为了升级自身，会先改写消费仓，再进入后续 plan/apply。备份与回滚却从 apply 才开始，因此同步器自身成为升级事务的例外。

**证据**

- 启动器先覆盖 `repo_sync.py`，再执行 init、prep，最后才进入 core 的 status/plan/apply：`repo/.repo_template/skills/repo-template-sync/SKILL.md:13-31`。
- core 明确承认 init/prep 会写入 state、脚本和入口：`repo/.repo_template/skills/repo-template-sync-core/SKILL.md:14`。
- 备份和回滚流程从 apply 才开始：`repo/.repo_template/skills/repo-template-sync-core/SKILL.md:33-34`。
- prep 会更新 core 和脚本，但不推进 `last_synced_commit`：`repo/.repo_template/tests/test_repo_sync.py:393-418`。

**影响**

在以下情况下，消费仓可能留下混合版本：

- prep 成功后，plan 发现无法裁定的共享文件。
- 用户放弃 apply。
- apply 因 active worktree 被拒绝。
- 新同步器与旧工具链之间存在能力或 schema 差异。

“尚未 commit”不等于具备可恢复性，尤其当消费仓原本还有未提交改动时。

**改进建议**

1. 优先在临时目录运行来源中的新同步器，避免预先覆盖消费仓。
2. 将自举、prep、apply 纳入同一个恢复基线和失败语义。
3. 明确覆盖“prep 成功后放弃 apply”的恢复流程。
4. 状态推进、文件写盘和提交审批应使用一致的事务叙述。

### H-06：同步自举示例不能覆盖宣称的来源类型

**结论**

文档宣称支持本地产物根、本地工厂根和 URL，但自举示例只适用于本地产物根。

**证据**

- 启动器正确说明工厂根脚本位于 `<src>/repo/.repo_template/scripts/`，产物根脚本位于 `<src>/.repo_template/scripts/`：`repo/.repo_template/skills/repo-template-sync/SKILL.md:11-14`。
- 随后的命令却始终复制 `$src/.repo_template/scripts/repo_sync.py`：`repo/.repo_template/skills/repo-template-sync/SKILL.md:15-21`。
- 初始化和首次接入允许 URL：`repo/README.md:41`。
- URL 的 clone/pull 缓存要到后续 core 阶段才出现，而启动器要求在任何 `repo_sync.py` 子命令之前先执行本地复制：`repo/.repo_template/skills/repo-template-sync-core/SKILL.md:20-22`。

**影响**

- 使用工厂根时，自举第一步路径错误。
- 使用 URL 时，没有先得到本地脚本的可执行文档路径。
- 离线或缓存缺失时，恢复行为不明确。

**改进建议**

1. 先把所有来源统一解析为本地“产物根”。
2. 命令只消费解析后的路径，不在复制步骤同时处理多种布局。
3. URL 先解析到受控缓存，再进入同一自举流程。
4. 为本地产物根、本地工厂根、URL 分别建立启动契约测试。

## 5. 质量、恢复与生命周期问题

### M-01：模板 contract 与业务验证未形成硬闭环

**结论**

模板 contract 是必要的工具链冒烟，但当前两个审批点可能把它当作充分验证：业务 task 收尾和模板同步提交。

**证据**

- 默认 `test_cmd` 只运行模板 contract：`repo/docs/blueprint/testing.md:3-9,20-26`。
- 默认 `blackbox_verify` 为“无”，文档明确说明不能替代业务验收：`repo/docs/blueprint/testing.md:30-34`。
- `task-work` 允许黑盒未定义时记录“未定义”：`repo/.repo_template/skills/task-work/SKILL.md:23-25`。
- 同步 apply 内置 contract 后，即可进入提交审批，没有强制消费项目自己的 `test_cmd` 和已定义黑盒：`repo/.repo_template/skills/repo-template-sync-core/SKILL.md:34-35`。

**影响**

- 新消费仓可能尚未配置业务测试，就把模板 contract 绿灯误解为项目质量绿灯。
- 模板升级可能改变工具链、共享配置和存量 workflow schema，但消费项目自身测试即使为红，也不阻碍同步提交审批。
- 独立 reviewer 可以发现部分问题，但不应成为配置门禁缺失的补救层。

**改进建议**

1. 保留 contract，用于验证模板工具链本身。
2. 增加一次性初始化确认：当前 testing 配置是“模板默认”还是“消费方已明确选择”。
3. 当 task 修改业务路径且 testing 仍为模板默认时，preflight 应阻断或至少要求明确确认业务验证策略。
4. 文档类或纯模板 task 可以显式豁免，不要求所有项目机械配置黑盒。
5. 同步提交前，除内置 contract 外，还应运行消费项目的 doctor、test 和已定义 blackbox。
6. “无黑盒”必须是消费方主动选择，而不是模板默认状态被静默继承。

### M-02：active task 缺少评审级别升级路径

**结论**

评审级别在创建期根据预期风险确定，但实际实施可能扩大风险范围。当前缺少清晰、文档化且符合 front matter 写权规则的 active 升级流程。

**证据**

- 创建期设置 `review_level`：`repo/.repo_template/skills/task-create/SKILL.md:17`。
- task-work 按既有 `review_level` 渲染和执行 review：`repo/.repo_template/skills/task-work/SKILL.md:27-29`。
- `task.py edit` 定位为修改 backlog task；active 的编辑路径没有形成可操作契约：`repo/.repo_template/scripts/repo_task/lifecycle.py:102-117`。
- 决策日志 L25 已承认分级规则仍存在博弈风险：`docs_repo/decision_log.md:41,63`。

**可构造场景**

一个普通 `single` task 在实施中发现需要修改鉴权、迁移或协议兼容逻辑。若仍按原级别收尾，实际风险与审阅深度不匹配。

**改进建议**

1. 允许 active task 在自身 worktree 中通过脚本执行 `single → full` 单调升级。
2. 升级后必须使旧 review 失效，并按 full 重新审阅最终范围。
3. 降级应采用更严格规则，不能与升级具有相同自由度。
4. reviewer 和实施者都应有义务在实际风险扩大时触发升级。
5. 不建议用单纯文件数量阈值代替风险判断；路径和 diff 只能作为提示信号。

### M-03：运行态和同步态缺少重建、迁移与可移植基线

**结论**

当前设计默认单机、单主仓、本机多会话，但文档没有把该边界和灾难恢复路径表达完整。

**证据**

- attempt ledger 和 goal 快照被 gitignore，仅保存在主仓：`repo/.repo_template/docs/usage.md:12-13`。
- cleanup/integrate 依赖 current exact attempt、terminal、report 和 handoff：`repo/.repo_template/skills/task-integrate/SKILL.md:11-22`。
- `.repo_template/sync_state.json` 被忽略：`repo/.gitignore:21-22`。
- state 同时承载模板源、最近同步 commit 和 `user_prompts` 等信息：`repo/.repo_template/scripts/repo_sync.py:1324-1327`。
- 没有 state 时，status/plan/prep/apply 报未初始化：`repo/README.md:41`。

**影响**

- runtime 丢失、换 clone 或换机器后，Git 分支和 handoff 可能仍存在，但标准 exact cleanup/integrate 无法直接闭环。
- 新成员缺少最近同步版本和保留决策，难以重现原维护者的同步行为。
- dirty 模板源允许写盘但不推进 commit 时，写入内容无法仅凭 state 中的 commit 重现。
- 固定 ref 升级、成功升级后的 downgrade/revert、URL 缓存离线使用缺少统一 runbook。

**改进建议**

1. 明确声明当前支持边界是单机、单 clone、本机多会话；不要暗示已支持分布式协作。
2. 增加从 Git 分支、task front matter 和 handoff 严格重建 ledger 的 recovery/import 路径。
3. 将同步信息拆分为：
    - 可入库、可共享的模板来源身份、resolved commit 和保留策略。
    - 不入库的本机路径、缓存和临时运行态。
4. 正式升级默认要求 clean 模板源；dirty 源仅作为显式开发模式。
5. 补充指定 commit 升级、revert 同步 commit、离线本地源和新 clone 重新接入的短流程。
6. 不需要为了这些问题立即引入统一 task 服务。

### M-04：默认队列和 goal 完成信号不符合用户心智

**默认队列问题**

无参数 `task-run` 按 tid 升序排列，同时要求依赖先于依赖者：`repo/.repo_template/skills/task-run/SKILL.md:15-18`。

合法任务图完全可能出现：

```text
t001 depends_on t002
```

此时默认队列为 `[t001,t002]`，第一个 start 就会被依赖门拒绝。依赖硬门能够阻止错误执行，但不能让默认入口本身可用。

现有 `plan` 已负责按依赖图计算计划：`repo/.repo_template/docs/architecture.md:33-41`。默认队列应复用同一拓扑结果，显式 tid 仍保持用户指定顺序。

**goal 完成信号问题**

goal 将 closed 和 integrated 都纳入完成集合：`repo/.repo_template/scripts/repo_task/goal.py:9-16`。因此 `GOAL_QUEUE_COMPLETE` 可能只表示执行和 cleanup 完成，并不表示改动已经合入主干。

merge 分离是正确授权设计，问题在于 `COMPLETE` 容易被理解成需求已经交付。

**改进建议**

- 默认队列复用 `plan` 的拓扑排序。
- goal 输出明确区分 execution complete 和 integrated。
- 完成输出列出 `awaiting_merge` 的数量和 tid。
- 保留现有退出码也可以，但必须把 marker 含义写清楚；不要自动 merge。

### M-05：多份权威文档已经发生实际漂移

**结论**

权威重复不再只是未来风险，当前已经出现相互矛盾的恢复和调用规则。

#### 例一：同步回滚语义相反

- core 写着内置 contract 失败后“保留已写入文件，不能声称已自动回滚”：`repo/.repo_template/skills/repo-template-sync-core/SKILL.md:34`。
- 现行测试契约要求“完整回滚、保留备份、state 不推进”：`repo/.repo_template/tests/test_repo_sync.py:665-686`。

这会直接影响 Agent 对现场的判断和后续恢复动作。

#### 例二：archive 只准新增与补审 amend 冲突

- 总则规定 `docs/archive/` 内部文件只准新增：`repo/AGENTS.md:20`。
- done 后 review 证据修复却要求 amend 已归档 task 的 review 过程文件：`repo/.repo_template/docs/usage.md:98`。

具体恢复规则应当作为总则的窄例外明确写出，而不是由执行者猜测优先级。

#### 例三：skill 调用图不完整

`repo/.repo_template/docs/usage.md:58-92` 存在以下问题：

- 内部 skill 表遗漏 `repo-template-sync-core`。
- 未列出多条真实边，例如 `bug-to-pending → task-create`、同步启动器到 core。
- 混入 CLI/reviewer 接口，和真正的 skill 组合关系放在同一层。
- 总表出现 `task-work → bug-to-pending analysis-only`，但 task-work 正文没有对应明确调用。

**改进建议**

1. 建立一张权威责任矩阵：
    - AGENTS 只保留长期不变量和写权。
    - architecture 只解释执行设计和原因。
    - usage 只保留入口、接口和组合关系。
    - SKILL.md 只保留本阶段动作、授权和停止条件。
    - 脚本输出和测试契约拥有具体机械恢复语义。
2. 每类规则只保留一份权威正文，其他位置使用链接。
3. 将 skill 组合图与 CLI/reviewer 接口分开。
4. 为回滚、归档例外、入口清单增加一致性契约检查。
5. 将决策日志 L24 转为具体整改项，不再仅写“持续盯”。

### M-06：pending、spec、spike 的附属生命周期仍有断点

这些问题不一定导致主流程立即失败，但会造成长期账目不一致。

#### pending 转 task 的闭环语义不统一

- `bug-to-pending` 默认路径建 task 后，没有与 `task-from-pending` 相同的 archive/fix-ref 步骤：`repo/.repo_template/skills/bug-to-pending/SKILL.md:13-25`。
- `task-from-pending` 要求 spec 写 pNNN，并通过 `archive --fix-ref` 归档：`repo/.repo_template/skills/task-from-pending/SKILL.md:17-19`。
- task-work 又只归档“已由本 task 闭环的来源 pending”：`repo/.repo_template/skills/task-work/SKILL.md:38-40`。

需要明确究竟采用“转 task 即归档”还是“修复完成才归档”。如果两种语义都保留，必须强制 pNNN 与 tid 双向链接，并为“不存在、已解决、重复”等非 task 闭环定义固定 resolution 格式。

#### specs_index 收尾依赖人工记忆

- AGENTS 要求每个 task 收尾更新 `docs/specs_index.md`，且“在表即生效”：`repo/AGENTS.md:9-10`。
- task-work 的 finalization 只泛指 specs、blueprint、guides 等文档，没有明确列出 specs_index：`repo/.repo_template/skills/task-work/SKILL.md:36-41`。
- specs_index 写“须已过黑盒”，但模板又允许黑盒为“无”或“未定义”：`repo/docs/specs_index.md:1-3`。

建议把 spec、specs_index、废弃归档和“黑盒未定义时能否生效”的口径纳入明确的 finalization 清单及轻量一致性检查。

#### spike 的条件式收尾没有接入 task 门禁

- AGENTS 要求 spike 有 report、结论进入 findings，完结后归档：`repo/AGENTS.md:18`。
- task-work 对 `UNVERIFIED-SPIKE` 只明确实验并改写标记，没有强制关联 sid、report、finding 或后续 tid：`repo/.repo_template/skills/task-work/SKILL.md:33,38-41`。

建议区分一次性 `.scratch` 实验与正式 spike。若建立正式 spike，收尾必须具备 report、finding、采纳结论和后续 tid 或无需后续 task 的理由。

## 6. 交付保障与采用成本

### M-07：缺少工厂 CI、宿主行为测试和明确支持矩阵

**工厂交付门禁**

工厂规则要求修改模板后运行全量测试，但当前主要依赖本地纪律。仓库树中未见工厂 CI 配置。消费仓 CI 已下线是有意决策，但不等于工厂也不需要机械交付门。

建议恢复**仅供工厂使用**的 CI：

```bash
pytest repo/.repo_template/tests -q
```

同时增加：

- 从 dirty 工厂工作区进行干净导出的初始化烟测。
- skill 软链和 OpenCode 入口检查。
- 至少一条完整 task 生命周期。
- 同步初始化、prep 中止和 apply 回滚场景。

CI 环境还应显式提供可选工具，避免 Node 等依赖缺失时测试跳过后仍把“全量绿”误解为所有路径均执行。

**宿主行为门禁**

当前跨宿主测试主要验证文件存在、软链、description 和 frontmatter，无法证明真实行为一致。

OpenCode 还需要明确版本契约：

- [OpenCode 稳定版文档](https://opencode.ai/docs/skills/)公开使用 `metadata.opencode/autoinvoke` 控制自动推荐。
- [OpenCode v2 文档](https://opencode.ai/v2/docs/skills/)明确支持顶层 `disable-model-invocation` 作为兼容字段。

因此，当前字段布局是否满足显式触发目标，取决于声明支持的 OpenCode 版本。该条属于兼容性风险，不是已复现故障。

**建议支持矩阵**

至少在 README 或 usage 中列出：

|维度|需要明确的内容|
|---|---|
|宿主与版本|Claude、Kimi Code、OpenCode 的最低版本和能力差异|
|OS/shell|Linux、macOS、WSL、Git Bash；原生 Windows 是否仅脚本层支持|
|基础工具|Python、Git、pytest、rsync、md_kx 的版本要求|
|可选工具|Node 是否仅工厂测试需要|
|网络|URL 模板源、GitHub issue、离线本地源分别需要什么|
|宿主能力|原生 Skill 调用、后台子代理、goal、hooks 是否为必需或可选|

### M-08：复杂能力缺少渐进披露，默认采用成本偏高

**结论**

当前主要使用成本不来自单个 skill 很长。各 SKILL.md 已经明显缩短，真正的问题是入口、状态概念和审批点同时暴露给用户。

**表现**

- 15 个 skill 全部通过软链或生成命令暴露，内部流程与用户入口并列。
- usage 将 12 个列为用户入口、2 个列为内部入口，却遗漏第 15 个 sync-core：`repo/.repo_template/docs/usage.md:58-82`。
- `task-work`、`task-integrate` 在表中是内部 skill，description 又允许用户直接调用，角色定义不一致。
- 消费侧没有充分解释“自然语言不会自动触发，必须显式调用”的授权设计。
- 初始化有 10 步，完成后缺少一个统一的“完成即绿”判据。
- 创建、调度、pending 等阶段分别询问 commit，低风险授权较碎片化。
- 单 task 典型路径包含创建 commit、执行 commit 和 merge commit；单独排程还会增加一次调度提交。

**改进建议**

1. README 只保留最短成功路径：

    ```text
    初始化并完成 doctor
    → /task-create
    → 无依赖单 task 可直接 /task-run tNNN
    → 用户批准后 integrate
    ```

2. 将依赖图、多会话、goal、attempt recovery、ledger、同步内部机制放入进阶参考。
3. 建立公开/内部角色注册表；如果不准备隐藏内部入口，就不要在文档中制造“内部即不可见”的错觉。
4. 对同一编排流程中的多个 commit，可以一次列出计划并取得批量授权，仍分别提交，减少重复询问而不改变审计边界。
5. 初始化末尾复用现有 doctor 和 contract，明确全部通过才视为完成。
6. 先通过文档和入口分层降低成本，不急于拆第二套模板或增加新的运行模式。

## 7. 不应误判为缺陷的设计取舍

以下设计具有明确背景，不建议在本轮整改中简单推翻：

### 7.1 worktree、attempt、goal 和一次执行 commit

这些机制已经在决策日志 L36 中明确保留。当前问题是组合、恢复和可观测性不足，不是这些概念必然应当删除。

### 7.2 merge 单独授权

`task-run` 的执行授权不包含 merge，是合理的安全边界。需要改善的是完成信号和批量授权表达，不是自动合并或自动 push。

### 7.3 `done` 但尚未 merge

这是正常中间状态，不应强行把 task 业务状态与主干集成状态合并。goal 的命名和输出需要区分二者即可。

### 7.4 工厂全量与消费 contract 分层

该分层本身合理。问题在于消费项目业务测试没有接到 task 和同步审批上，而不是必须让消费仓运行全部工厂集成测试。

### 7.5 单机和本机多会话

如果模板明确面向个人本机使用，该设计可以成立。需要补齐支持边界和恢复路径，而不是立即引入中央状态服务。

### 7.6 简单任务的固定成本

`review_level=single`、删除 `plan.md`、减少额外全仓扫描已经降低部分成本。不建议重新提出 `review_level=none`、全局 main 直做、`no-worktree` 或多执行 commit 作为默认整改方向。

## 8. 建议实施顺序

### 第一阶段：先修正确性、安全和核心可执行性

对应问题：H-01、H-02、H-03、H-04、H-05、H-06、M-02。

目标：

- 初始化只分发干净产物。
- 父子 skill 在受支持宿主上有可执行、可验证的组合契约。
- 合并不破坏依赖图。
- 同一 task 不会被两个执行者同时接续。
- 同步自举、prep 和 apply 具有统一恢复语义。
- 风险扩大时可以升级评审级别。

### 第二阶段：补业务门禁、恢复和默认路径

对应问题：M-01、M-03、M-04、M-05。

目标：

- 模板 contract 不再被误认为业务验证。
- 同步审批同时检查消费项目自身门禁。
- runtime 或 sync state 缺失时有明确恢复路径。
- 默认队列遵守依赖拓扑。
- goal 完成信号区分执行完成与已经集成。
- 回滚、archive 和调用图只剩一份权威语义。

### 第三阶段：补附属生命周期和采用体验

对应问题：M-06、M-07、M-08。

目标：

- pending、spec、spike 的闭环规则一致。
- 工厂 CI 覆盖完整测试和关键端到端场景。
- 支持矩阵明确宿主、OS、工具版本和可选能力。
- README 提供最短成功路径，复杂机制按需加载。
- 低风险审批可以批量说明，但不减少危险操作授权。

## 9. 建议新增的端到端验收场景

以下场景比继续增加静态文本断言更能覆盖本次发现的问题：

|场景|必须验证的结果|
|---|---|
|dirty 工厂工作区初始化|secret、runtime、sync state、宿主状态均不进入新仓|
|三宿主父 skill 调子 skill|显式用户授权保留，父子链可执行，参数与 identity 不变|
|自然语言触发高风险 skill|不会绕过显式授权|
|合并具有下游依赖的 backlog|依赖改指目标，不丢失、不自依赖、不成环|
|两个会话恢复同一 running task|只允许一个执行者进入 task-work|
|prep 成功后放弃 apply|现场可恢复，不留下无说明的混合版本|
|三种模板来源自举|产物根、工厂根、URL 都走统一解析路径|
|未定制 testing 的首个业务 task|不会把模板 contract 当作业务验收|
|active single task 扩大到高风险面|能够升级 full，并重新审阅最终范围|
|ledger 丢失但 Git/handoff 完整|能经严格校验重建，或得到明确不可恢复诊断|
|t001 依赖 t002 的默认队列|默认执行顺序符合拓扑，不依赖用户手工调整 tid|
|goal 完成但尚未 merge|输出清楚显示 awaiting_merge，不伪称已交付主干|
|同步后消费项目测试失败|阻止同步提交审批，并如实报告 state 和文件现场|
|archive 中补审证据修复|只走明确窄例外，不破坏其他归档只增规则|

## 10. 最终建议

当前最合理的方向不是继续扩张工作流，也不是大规模拆除已有机制，而是进行一次以端到端契约为中心的收敛：

1. **先让现有主路径可靠运行。** 修复初始化、skill 组合、依赖保持、执行互斥和同步恢复。
2. **再让验证结果具有真实含义。** 区分模板 contract、消费项目测试、黑盒和 review，避免形式绿。
3. **让状态能够恢复。** 明确单机边界，提供 ledger、同步状态和新 clone 的重建路径。
4. **让权威文档彼此一致。** 恢复语义、归档例外和调用关系不应依赖执行者猜测优先级。
5. **最后降低认知成本。** 通过公开/内部入口分层、最短路径和支持矩阵改善体验，而不是增加更多模式。

完成上述工作后，现有严格模板、worktree、attempt、goal、独立 review 和同步能力才有稳定基础继续保留和演进。
