# docs_repo 全量审阅意见（k3）

审阅范围：`11111.md`、`workflow_session_analysis_2026-07.md`、`workflow_record.md`、`workflow_feedback.md`、`workflow_retrospective.md`、`workflow_retrospective_0.md`、`archive/workflow_skill_split_proposal.md`。

总体判断：这批文档构成一条完整的"理论 → 实战 → 会话实证 → 事故 → 结构方案"演进链，质量高于一般复盘——有数据、有根因分层、敢写自我归因。但存在**跨文档结论冲突未裁决**、**根因分析深浅不一**、**行动项落地率存疑**三个系统性问题。以下按文档逐一给意见，最后给跨文档总评与行动建议。

## 1. `workflow_session_analysis_2026-07.md`（最新、数据最硬，质量最高）

**优点**

- §1 审阅信噪比的四层根因（角色保守偏差 / 信息不对称 / finding 无锚 / 同模型不解决盲区）是全 repo 最锋利的一段分析。尤其"换模型不解决问题，根因在 prompt + 上下文 + 阈值设计"——直接排除了"换 sonnet 当 reviewer"这条偷懒路径，方向正确。
- 数据引用规范（会话 ID + 行号 + 比例），结论可回溯。
- "亮点"一节不是客套，是真的在区分"该保留什么 vs 该改什么"。

**问题**

- **建议密度过高，优先级标注与因果权重不匹配**。P0 三条建议（reviewer AC 硬阈值 / prompt 注入决策上下文 / Step 2 AC 断言清单）本质是同一件事——给 reviewer 一个判定锚点。应合并为一条主建议 + 两个支撑动作，现在拆成三条平列，读者难以判断最小可行改动是哪个。
- §2 "`/goal` hook 致 context 溢出"的归因**只到现象层**。19MB 会话、0 条 isCompact、手动 `/clear` 接力——这些是症状。根因是"hook 把'串行推进多 task'这个工作流决策硬编码成了不可中断的 Stop 指令"，建议（每 task 切会话）是对的，但文档没说清为什么 hook 当初被设计成这样、是 hook 机制本身的问题还是这条 hook 配置的问题。不改 hook 机制，换个项目还会复发。
- §8 ABI 脚本、§9 工具误用、§10 打包验证、§11 分支卫生——四条 P2 堆在一起，每条一两行建议，**没有一条指出共同模式**："所有这类问题都是'agent 在脚本/工具边界上的假设未被显式校验'"。合并成一条"脚本与工具边界需自检产物而非依赖退出码"更有力。

**行动建议**

- §1 三条 P0 建议合并为：review prompt 注入「AC 断言清单 + 已判定不测分支清单 + 硬阈值：只报 AC 阻塞级」。这是单一改动点，收益覆盖三层根因。
- §2 建议补一条：审查 `/goal` hook 的设计意图——它要解决什么问题、能否用"每 task 完成时提示用户"替代"强制 Stop 串行"。

## 2. `workflow_feedback.md`（理论分析，与 retrospective 系列部分重叠）

**优点**

- §1 spec/plan 字段重叠的诊断准确（"plan 退化为 spec 副本"），§"spec/plan 边界的再评估"一节按**读者**而非字段语义重划归属，是比初版更根本的框架，方向正确。
- "一个根本性的观察"（防错导向 vs 效率导向的失衡）点破了整套工作流的设计哲学问题，这句话应该提到文档最前面而不是埋在倒数第二节。

**问题**

- **改进建议 A（plan 分三套模板）与文末"spec 收编决策上下文，plan 只留 agent 私有笔记"自相矛盾，文档自己也承认了（"两者部分冲突"），但没给裁决**。"测试策略归 spec 还是归 plan_code"的最终判断（归 spec）是对的，但前面 A 节仍完整保留 plan_code 三套模板的方案，读者不知道当前立场是"A 已废弃"还是"A 与再评估并存择一"。应明确标注：A 中 `plan_doc` / `plan_style` 仍有效，`plan_code` 的测试策略字段已被再评估收编进 spec。
- 建议 B（task 粒度改为"一主题 N commit"）与 `workflow_retrospective.md` §7 的结论一致，但与当前 CLAUDE.md「执行期：一个 task 一个 commit」硬冲突。**两份文档都提议推翻同一条现行规则，而 CLAUDE.md 至今未改**——这说明建议提了但没闭环。这类"建议与现行规则冲突"的条目应单独建一个待裁决清单，否则永远停在纸面。
- §4 "tasks_index.json 是高成本同步点"与 §E "简化索引"给了两个方案（archive-only / 放开硬约束），但 `workflow_retrospective.md` §1 给了三个方案（main 维护 / front matter derived / 不切分支），`11111.md` 又说"统一 task 服务，用户决定"。**同一个问题在三个文档里有六套方案，无一被选定**。这是最典型的"分析充分、决策缺席"。

**行动建议**

- 在文末"待决策项"基础上加一列"推荐默认"：作者已有倾向（如方案 C 不切分支），应直接写出推荐而非六个方案平列。复盘的价值在结论，不在穷举。

## 3. `workflow_retrospective.md`（t041-t061 实战复盘）

**优点**

- §1 多分支 merge 冲突是全文最有价值的一节——"11 分支同 base 切出，finish 都改同一对 JSON，merge 必然冲突"，根因讲得干净，方案 C（不切分支直接 main 上做）有 t048/t049/t051 共 10 个 task 的实证支撑，可信。
- §5 批量缩进破坏测试、§6 spec AC 与环境脱节——这类"只有实战才会踩到"的问题正是复盘该写的，与 feedback 的理论层互补良好。

**问题**

- **方案 C 与本仓 `workflow_record.md` 的事故教训直接冲突，两份文档必须放在一起读**。retrospective 说"所有 task 直接在 main 上做零冲突"；workflow_record 记录的是"共享工作区被切走导致 t071 未提交改动全丢"。两者不是简单对立——retrospective 的场景是**串行**做 task（做完一个 commit 再做下一个），workflow_record 的场景是**并发/交错**（t071 未提交时主目录被切去处理 t102）。结论应是：**串行可 main 直做；任何并发/交错必须 worktree**。两份文档都没写出这个合并结论，各自读者会拿到片面行动指南。
- §2 "11 个 task 直接收尾跳过审阅"被当作"审阅浪费"的证据，但也可以反向解读：这 11 个 task 跳过审阅后**没有出事故**，恰恰证明分级早该做、且 agent 的自行分级判断是准的。文档只取了前一种读法。建议补一句：跳过审阅的 task 事后零回归，可作为分级规则的实证基线。
- §3 "max_review_round=2 不够，剥洋葱式收敛"与 `workflow_retrospective_0.md` 痛点 5 讲的是同一件事的两个面：retrospective 说"复杂 task 要 5 轮"，retrospective_0 说"round N 新 finding 不该强制 N+1"。**真正的问题是 round 计数语义不清**——"轮"到底计"reviewer 出场次数"还是"finding 处置闭环次数"？两份文档都在调数字，没人改语义。建议：`max_review_round` 应限定为"同一批 finding 的回归轮次"，新 finding 重置计数或走快速通道。

## 4. `workflow_retrospective_0.md`（t001-t007 首跑复盘，finding 分类表最有价值）

**优点**

- 开头 39 条 finding 的分类表（真 bug 28% / spec 过时 10% / 重复模式 10% / nitpick 15% / 测试缺口 36%）是三份 retrospective 中唯一对 finding **本身**做质量分类的。这个分类方法应沉淀为 review 报告的标准字段——每条 finding 标注类别，撤回率/噪音率就能自动统计，不必等复盘时人工归类。
- "根因：发现横向需求时默认绕过+标遗留"一节把痛点 2/4/6 收敛到单一根因，且诚实写了"为什么没开"（scope 守过头 / goal 推进压力 / 没第一时间识别系统性）——这是全 repo 自我归因写得最好的一段，因为它分析的是**决策时的认知状态**，不是事后现象。

**问题**

- 痛点 1"spec 写死技术细节 → 工具演进 → spec 过时 → FAIL 循环"的改进方向（spec 只写行为 AC、技术选型落 ADR）正确，但与 `workflow_feedback.md` 的"按读者切"框架存在术语漂移：这边叫"行为 AC vs 技术选型"，那边叫"契约区 vs 上下文区"。同一概念的多种叫法会让后续执行者困惑。**建议全 repo 统一为 feedback 的"契约区 / 上下文区"术语**，retrospective_0 这节的结论自然并入。
- 痛点 7"AC 三处维护"建议"task.md 引用 spec AC 不复制"——这条已经可以直接执行，零风险零争议，却和需要决策的大改动混在同一个汇总表里。汇总表应分"可直接执行"与"需用户裁决"两栏。

## 5. `workflow_record.md`（t071 事故单点记录）

**优点**

- 这是事故报告该有的样子：已确认事实 / 推断但不断言（reflog 无法识别执行者、不能断言 reset 参数）/ 责任归属 / 防护顺序，四层分得清。"严格说，单独执行普通 git switch 通常会拒绝……不能断言具体参数；结果已确认"——这种区分"确证 vs 推断"的写法值得所有复盘文档学习。

**问题**

- **结论只覆盖了事故的一半**。"应创建独立 worktree"是对的，但没回答：为什么流程允许 agent 在"工作区已有 t110 未提交文档、索引可能被并发修改"的明显信号下，仍然只建 branch 不建 worktree？§3 说"我错误地把已创建分支当成足够隔离"——这是个体失误归因。流程层的问题是：**CLAUDE.md 至今没有一条"task 开干前必须检查工作区污染度并决定隔离级别"的硬约束**（session_analysis §11 提了 Step 1 强制 `git status` 校验，是对的，但那是另一份文档）。事故报告的"后续防护"一节只写了恢复顺序，没写流程修补——第 5 节应加一条：将"开干前工作区检查 + 并发时强制 worktree"写入 tasks-run skill 或 CLAUDE.md，否则同类事故必复发。
- 这份文档的文件名（`workflow_record.md`）与内容（单一事故报告）不匹配，也与其他文档的命名风格（`workflow_retrospective*` / `workflow_feedback`）不一致。建议改名 `incident_t071_worktree_loss.md` 或移入 `incidents/` 子目录。

## 6. `archive/workflow_skill_split_proposal.md`（已归档方案）

**优点**

- "不解决的问题"一节是全文最有价值的部分——明确承认 skill 无程序级强制力、不能保证每步执行、关键限制仍靠脚本/hook。这种"先说清边界再谈方案"的写法避免了 skill 被误当成安全边界。

**问题**

- 从归档状态看方案已被采纳并实施（现行 CLAUDE.md 确有 tasks-run / task-create skill 体系），但文档内"未来实施顺序"和"实施判定标准"仍是将来时。**归档时应补一节"实施结果对照"**：判定标准 6 条逐条标注达成/未达成/偏离原因。否则后人无法判断这份方案是"完整落地"还是"部分落地后归档"，参考其做下一次拆分时缺少校准数据。

## 跨文档总评

### 三个系统性问题

**1. 同一问题多文档重复诊断、结论互不引用、方案平列不裁决**

tasks_index 冲突问题在四个文档里出现（feedback §4/E、retrospective §1、11111 第 3 条、session_analysis §12）；审阅成本问题在三个文档里出现（feedback §3/C、retrospective §2、retrospective_0 痛点 3）；max_review_round 语义问题在两个文档里以不同角度出现。每份文档都自洽，但**没有任何地方维护"问题 → 各文档结论 → 当前裁决状态"的总索引**。docs_repo 需要一份 `index.md` 或 `decision_log.md`：每个被两次以上诊断的问题一行，记录各文档出处、方案清单、当前状态（已落地 / 待裁决 / 已否决）。否则第四份复盘还会重新诊断一遍 tasks_index 冲突。

**2. 建议与现行 CLAUDE.md 规则的冲突没有显式追踪**

至少四处建议直接要求修改现行硬规则：task 粒度改"一主题 N commit"（feedback B / retrospective §7）、审阅分级（feedback C / retrospective §2 / retrospective_0 痛点 3）、reviewer finding 加 AC 硬阈值（session_analysis §1）、task 分支策略（retrospective §1 vs workflow_record）。这些建议与 CLAUDE.md 条款冲突时，应有一个明确的"提案 → 裁决 → 改规则 → 验证"通道，而不是散落在复盘文档里等待被想起。当前状态是：复盘写了、CLAUDE.md 没改、下次项目照旧踩坑。

**3. 根因分析深浅不一：有的到认知层，有的停在现象层**

好的样本：session_analysis §1（四层根因到角色 prompt 与信息结构）、retrospective_0 根因节（到决策时认知状态）、workflow_record（确证与推断分层）。差的样本：session_analysis §2（hook 问题停在"串行导致溢出"，没到 hook 设计意图层）、retrospective §3（停在"轮次不够"，没到 round 语义层）。**判断标准可以很简单：如果根因分析的结果不能推出一个"改哪个具体 artifact（prompt/规则/脚本）"的动作，就是还没到层**。建议后续复盘用这个标准自检。

### 内容本身的技术判断

- 全部文档对工作流"防错 vs 效率"失衡的诊断是一致的，且方向正确：审阅分级、task 粒度放宽、plan 瘦身、reviewer 加锚点。这些改动若落地，按 retrospective_0 的 finding 分类数据估算，可消除约 35-45% 的无效 review 开销（spec 过时 10% + 重复模式 10% + nitpick 15% + 部分测试缺口）。
- 唯一需要警惕的反向风险：**分级规则本身会变成新的博弈点**。审阅按 risk_level 分级后，agent 有动机把 task 标低级别以跳过审阅；task 粒度放宽后，"一主题"的边界会被不断撑大。两条建议落地时都必须配校验机制：risk_level 由 reviewer 复核或 task.py 按文件数/路径启发式校验；task 主题由 spec 验收标准条数上限约束（如 >6 条 AC 强制拆）。

### 文档管理建议

- 命名与分层：`workflow_record.md`（事故报告）与 retrospective/feedback/analysis（定期复盘）是不同文体，应分目录或统一命名前缀（`incident_*` / `retro_*` / `analysis_*`）。
- 时效标注：feedback 文末的"再评估"补充节模式很好（注明是对 §1 的发展而非否定），建议推广——所有被后续文档修正的结论，在原文标注"本文 §X 已被 YYY 文档 §Z 发展"，替代静默的多版本并存。
- `11111.md` 按上文分流后删除。

## 一句话结论

**这批文档的诊断能力已经超过工作流本身的问题——缺的不是更多复盘，而是一张跨文档的"问题/结论/裁决状态"总账，以及"建议冲突现行规则时如何改规则"的闭环通道。先建总账，再落地四条规则级改动（审阅分级、reviewer AC 锚点、task 粒度、分支/worktree 策略合并结论），其余建议自然归位。**
