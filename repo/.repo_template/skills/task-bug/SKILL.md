# task-bug

Bug 分析与修复立项入口。复现、定位根因、扫同类位点、做补测分析，登记 `pNNN`，再按 `task-create` 建 backlog 修复 task。不在本 skill 内改生产代码。连续口述多条待办且 bug 只需分析登记、暂不立项时，用 `pending-record`（其 bug 路径复用本 skill 第 1–6 步）。

## 步骤

1. **收敛现象**。确认期望 vs 实际、影响范围、是否回归、相关 tid/日志。信息不明就问用户，不靠猜测下结论。

2. **复现（仅 `.scratch/`）**。最小复现；临时脚本与过程笔记写 `.scratch/`（已 gitignore）。

    - 复现失败：汇报已尝试的路径与卡点，停下；不硬登记。

3. **根因**。定位到可验证的机制（代码路径 / 配置 / 数据 / 环境），并归类：产品缺陷、环境问题、配置问题、测试假绿等。

4. **同类位点扫描（必做）**。根因确认后，按同一机制在仓库内找是否还有相同 bug，有则一并分析并**合并**进本次结论（默认一条 pending / 一个修复范围，不按文件拆多条）。

    - **怎么找**：以第 3 步机制为轴——同一 helper/API 误用、同一校验缺失、同一错误默认值、复制粘贴块、对称模块（create/update、读写路径）、相同配置键/分支条件等；用搜索与对照阅读，不靠臆测「可能还有」。
    - **逐处判定**：
        - **同因成立**：写出路径/符号 + 机制如何同样适用（必要时在 `.scratch/` 补最小对照；不强制每个位点都完整复现，但必须可验证，不能只写「看起来像」）。
        - **同因不成立**：一句理由丢弃，不写进合并范围。
        - **吃不准**：单列「待确认位点」，汇报时问用户或标进条目供后续核实；**不**默认算已确认同类。
    - **合并结果**（写入后续步骤的输入，禁止每个同类位点各建一条 pending，除非机制实质不同、修复策略必然分叉——分叉时拆条并互相引用）：
        - **现象**：主报告点 + 已确认同类位点的可观察差异（若有）。
        - **影响**：并集（功能面、调用面、模块列表）。
        - **根因**：共享机制 + 分类 + **已确认位点清单**（路径或符号）。
        - **测试缺口 / 补测**：覆盖主点与全部已确认同类位点，避免只补一处仍漏其余。
    - 扫完无同类：在根因或汇报中显式写「已扫，无已确认同类位点」及检索轴（搜了什么模式），避免沉默跳过。

5. **测试缺口分析（必做）**：

    - 现有测试为何没盖住（无测 / 弱断言 / mock 掉被测逻辑 / 只测假路径 / 缺集成层等）——对主点与第 4 步已确认同类位点一并看。
    - 应如何增删修改测试（层级、场景、断言对象）；补测须能挡住清单内各点，而非只挡首发路径。

6. **登记到 pending**。根因与同类扫描结论确认后用 `.repo_template/scripts/pending.py new --slug <主题> --kind bug` 在 `docs/pending/todo/` 建条目并填写；已有条目就地更新内容，保留原文件与 `pNNN`：

    - 现象：期望 vs 实际，复现步骤（含同类位点差异若有）
    - 影响：受影响功能与范围（合并后的并集）
    - 根因：可验证机制 + 分类 + 已确认同类位点清单（或「已扫无同类」）
    - 测试缺口：第 5 步结论（为何没 catch + 覆盖各点的补测方向）
    - 线索：`.scratch/` 路径
    - 处理：未开

7. **汇报根因，等待用户审批立项**。简明汇报：根因机制与分类（第 3 步）、同类位点合并结论（第 4 步：清单或已扫无）、测试缺口（第 5 步）、影响范围与拟建修复 task 的范围（须覆盖已确认同类位点），请用户批准立项。批准进入第 8 步；拒绝或暂缓则跳过第 8 步，直接进第 9 步提交 bug 总账（不建 task，保留 `pNNN`）。

8. **建修复 task**（仅用户已批准立项）。产品缺陷或测试假绿已确认后，链式调用 `task-create`：

    - spec 上下文区用结构化 `来源` 字段写 `pNNN`；
    - 写清根因、**已确认同类位点**、补测方向、风险与回退；行为 AC / 范围须覆盖合并后的修复面，避免只修首发点；
    - task 保持 `backlog`，生产修复交给 `task-run` 调度执行；
    - 环境或配置问题无需改仓库时，不建修复 task，保留 `pNNN` 并汇报所需外部动作。

9. **询问提交 bug 总账**。列出本次新增或更新的 `docs/pending/todo/{pNNN}_{slug}.md`：

    - 已批准立项：**task 目录与派生 index 由 `task-create` 在全部 task 落盘自检后的统一创建 commit 提交；bug 条目文件单独 commit，不与 task 目录合并**。本步只提交 bug 条目文件。
    - 拒绝/暂缓：无 task；只提交 bug 条目文件。
        `.scratch/` 已 ignore，不入 commit。

## 边界

- 复现/探索代码**只许** `.scratch/`；禁止写未 ignore 路径（`src/` `tests/` `scripts/` 等）。
- 不 `start`，不做生产修复；未获用户批准立项不建修复 task。
- 后续编码走 `task-run`；环境或配置问题按第 8 步汇报外部动作。
- 同类扫描不得把「风格相似」或未验证路径并入修复范围；吃不准的进待确认，不默认同因。

## 完成

汇报：`pNNN`、修复 task tid（若用户批准立项且需仓库改动）、根因一句话、已确认同类位点数与清单（或已扫无）、补测要点、`.scratch/` 线索路径。自检：生产树无修复 diff，task 未 start。
